## Что это закрывает (сценарии из обсуждения)

1. **«Продал 4 из 8, рестарт»** — раньше тихий цикл не сохранял CLOSED-статусы:
   рестарт возвращал проданное как фантомные OPEN → вечный `RECONCILE_MISMATCH`.
   Теперь (В1) state.json пишется в конце КАЖДОГО цикла, окно устаревания —
   максимум один цикл (30 с).
2. **«Обрыв при активной заявке, исполнение офлайн»** — (В2) если у брокера
   позиции нет, но в реестре есть своя SELL-заявка закрытия, созданная ПОСЛЕ
   входа (или `close_order_id` в самой позиции), учёт закрывается автоматически,
   CSV-строка пишется с реальной ценой исполнения. Без оператора.
3. **«Ручная продажа зависших позиций»** — (В3) позиция активна локально,
   у брокера её нет, своей SELL нет → первое обнаружение только фиксирует
   подозрение, второе подтверждение (следующая сверка) закрывает учёт как
   `EXTERNAL_CLOSE` с приблизительной ценой и пометкой в `error_note`.
   Заморозка новых входов снимается автоматически.
4. **«WUSH/TRMK: отчёт не привязан к RECOVERY»** — (В4) адоптированная
   RECOVERY-позиция привязывается к единственному BUY-отчёту по FIGI с
   `executed_lots == quantity`; после привязки промоция RECOVERY→OPEN идёт
   штатно (цена входа/SL/TP восстанавливаются). UNCERTAIN-запись реестра не
   перезаписывается в обход P0-5 — снимается штатно после подтверждённой сверки.
5. **Ступень 1 доходности (С1)** — безубыток/трейлинг ГОТОВЫ, но **выключены**
   (`BE_TRAIL_ENABLED=False`). Экстремумы MAE/MFE берутся только из
   high/low 5-минутных свечей (поллинг 30 с внутрибарные экстремумы пропускает).

## Гарантии, которые НЕ ослаблены

- Брокер — истина; недостоверный снимок (`None`) учёт не меняет.
- Все прежние fail-closed блокировки (UNCERTAIN, недостоверный реестр,
  `state_save_failed`, unknown-FIGI) работают как прежде.
- «Воскрешение» закрытых сделок по-прежнему запрещено
  (`closed_entry_order_ids` проверяется и в В2-поиске, и в В4).
- Расхождения по количеству/направлению по-прежнему замораживают входы.
- В3 срабатывает только на **двух последовательных** достоверных снимках.

## Установка

```powershell
# 1. Резервная копия текущей рабочей папки
Copy-Item -Recurse . ..\backup_v2.2_before_stage1

# 2. Заменить 4 файла в рабочей папке (или запустить сборку целиком из новой папки)
#    config.py, logger.py, execution.py, main.py

# 3. Тесты (из корня папки)
pytest tests/ -v

# 4. Запуск как обычно: python main.py   (trading.flag НЕ создаётся автоматически)
```

`.env` и `trading.flag` остаются в рабочей папке — в пакет не включены.

## Что произойдёт при первом запуске с текущим state.json

- **WUSH/TRMK** (RECOVERY, адоптированные): если позиции уже проданы вручную —
  reconcile закроет учёт как `POSITION_RECOVERY_CLOSED` (чисто, без CSV).
  UNCERTAIN-записи этих BUY в order_ledger.jsonl остаются нетерминальными и
  продолжают блокировать BUY только по этим двум FIGI — убираются штатной
  процедурой чистки журнала (вариант А/Б), автоматом их разрешать нельзя.
  Если позиции ещё есть у брокера — В4 привяжет их к заявкам, цена входа
  восстановится, позиции перейдут в OPEN под штатный SL/TP.
- **research_trades.csv**: шапка не совпадёт с новой схемой → авто-миграция:
  старый файл → `research_trades_YYYYmmdd_HHMMSS.bak.csv`, новый пустой с новой
  шапкой. `cumulative_net_pnl_rub` начнётся с нуля (старый журнал рядом).
- При старте появятся события `STARTUP_RECOVERY`, `RECONCILE_OK` — это норма.

## Чек-лист полевого теста (по пунктам вашего вопроса)

1. [ ] `pytest tests/ -v` — весь набор зелёный (в песочнице, до старта).
2. [ ] Старт без trading.flag: в логе `[reconcile]`, `state.json` обновляется
       каждые ~30 с (проверить mtime: `dir state.json` дважды с интервалом).
3. [ ] **Сценарий В2**: открыть позицию → снять trading.flag → отправить
       рыночную SELL вручную через скрипт (или убить процесс сразу после
       CLOSE_SENT) → рестарт → ожидать `POSITION_CLOSED_BY_LEDGER` + строка в
       CSV с реальной ценой выхода, входы разблокированы.
4. [ ] **Сценарий В3**: при работающем роботе продать одну позицию вручную в
       песочнице → ожидать два уведомления: `POSITION_EXTERNAL_CLOSE_SUSPECTED`
       (учёт не тронут) и через цикл `POSITION_CLOSED_EXTERNAL` + CSV с пометкой
       EXTERNAL_CLOSE. Никаких вечных `RECONCILE_MISMATCH`.
5. [ ] **Сценарий В4**: перезапуск с текущими WUSH/TRMK (если ещё в портфеле)
       → `RECOVERY_ENTRY_BOUND` → `POSITION_RECOVERY_RESOLVED` (OPEN с SL/TP).
6. [ ] **Сценарий В1**: любое закрытие по SL/TP → через 30 с в state.json
       позиция уже `CLOSED` (раньше оставалась OPEN до следующего входа).
7. [ ] После 2–3 дней стабильной работы можно включить С1:
       `BE_TRAIL_ENABLED = True` в config.py (появятся логи
       `BE trigger r_peak=...` / `TRAIL — SL ...`, в CSV — причины `BE`/`TRAIL`).

## Честные ограничения (не закрыты этой версией)

- **Пока робот офлайн, SL/TP не существуют на бирже** — защита от движения
  цены в офлайне не появляется (это архитектурный вопрос биржевых стоп-заявок,
  отдельный этап). Минимум: авторестарт процесса (systemd/supervisor).
- Редкий остаточный кейс: UNCERTAIN-позиция разрешается через
  `resolve_uncertain` с пустой ценой выхода → CSV может быть пропущен
  (executed_lots=0) — прежнее поведение, не менялось.
- События `POSITION_RECOVERY_CLOSED`/UNCERTAIN-записи старых сделок сами себя
  не чистят — разовая чистка журнала (вариант А/Б) остаётся на операторе.
